# Архитектура

Read-only GraphQL API, отдающее профиль специалиста и связанные с ним данные:
навыки, опыт работы, проекты. Мутаций нет — визитка не редактируется через API,
содержимое приходит из сида при старте.

## Слои

```
резолвер  ->  сервис  ->  репозиторий  ->  Prisma
```

Направление зависимостей одностороннее, вверх никто не смотрит.

| Слой | Отвечает за | Не знает про |
| --- | --- | --- |
| резолвер | приём запроса, аргументы, вызов сервиса | базу, Prisma |
| сервис | бизнес-логику, маппинг строк в модели API | GraphQL, HTTP |
| репозиторий | запросы к базе | GraphQL, бизнес-правила |

**Модели Prisma наружу не отдаются.** Между строкой таблицы и типом GraphQL стоит
маппер. Благодаря этому колонка `full_name` отвечает полем `name` — именно так
поле названо в примере запроса из задания.

## Модули

```
profile     корневой запрос и поля профиля
skills      справочник навыков
experience  места работы и достижения
projects    проекты, ключевые пункты, обратная связь навык -> проекты
prisma      клиент базы
health      проба для docker
common      настройки GraphQL, правило глубины, доменные ошибки, утилиты DataLoader
```

`PrismaModule` **не глобальный**: каждый потребитель импортирует его явно. Так по
списку `imports` виден настоящий граф зависимостей, а не «оно откуда-то есть».

Обратная связь `Skill.projects` живёт в модуле проектов, а не навыков. Положи её
в навыки — модули начали бы ссылаться друг на друга по кругу.

## GraphQL

Схема описывается кодом (code-first): классы с декораторами `@ObjectType`, из них
генерируется `schema.gql`. Один источник правды, схема не может разъехаться с
типами.

**Один корневой запрос**, строго по формулировке задания:

```graphql
type Query {
  profile: Profile!
}
```

Поле называется `experience` в единственном числе — как в примере из задания.
Фильтры вынесены на вложенные поля, а не в новые корни:

```graphql
profile {
  skills(category: INFRA) { name }
  projects(kind: GAMEDEV, featured: true) { name }
}
```

### Резолверы полей и ленивость

Вложенные данные разрешаются отдельными резолверами (`@ResolveField`), а не через
`include` в корневом запросе. Не спросил клиент про опыт — в базу за ним никто не
сходил:

| Запрос | SQL-запросов |
| --- | --- |
| `profile { name }` | 1 |
| `profile { name skills { name } }` | 2 |
| опыт + навыки + достижения | 5 |
| профиль со всей вложенностью | 11 |

### N+1 и DataLoader

Связи «многие ко многим» между навыками и опытом/проектами создают классический
N+1: на каждое место работы ушёл бы отдельный запрос за его навыками. Решается
через DataLoader — он копит вызовы внутри одного тика event loop и делает один
запрос `WHERE experience_id IN (...)`.

Лоадеры объявлены со `Scope.REQUEST`: кэш живёт ровно один HTTP-запрос. Оставь их
синглтонами — ответы залипали бы между запросами, а память росла бы бесконечно.

Свойство закреплено e2e-тестом: он считает запросы через `prisma.$on('query')` и
требует ровно один запрос на каждую связанную таблицу. Тест проверен на способность
падать — с отключённым батчингом он показывает два запроса вместо одного.

Оговорка: `include` в Prisma выполняется отдельным запросом, а не соединением
таблиц, поэтому связка через промежуточную таблицу стоит двух запросов вместо
одного. Стратегия загрузки через JOIN в Prisma 7 с driver adapter недоступна. На
N+1 это не влияет — счётчик остаётся постоянным и не растёт с числом строк.

### Ограничение глубины

Граф цикличен: навык -> проекты -> навыки -> и так далее. Клиент может закрутить
сколь угодно глубокий запрос и положить сервер. Глубже 10 уровней запрос
отклоняется собственным правилом валидации
(`src/common/graphql/max-depth.rule.ts`).

Правило разворачивает фрагменты — спрятать за ними глубину не выйдет — и не
считает служебные поля интроспекции, иначе песочница перестала бы открываться.

Готовая библиотека для этого не подошла: её тип плагина собран под предыдущий
мажор Apollo Server, а ошибку она бросает не как `GraphQLError`, из-за чего Apollo
маскировал причину под «внутреннюю ошибку сервера».

### Ошибки

Сервисы бросают доменные ошибки, которые ничего не знают о транспорте
(`common/errors/domain.errors.ts`). Перевод в коды GraphQL живёт на границе, в
`formatError`. Без этого `NotFoundError` уезжала бы клиенту как
`INTERNAL_SERVER_ERROR`: всё, что не `GraphQLError`, Apollo считает сбоем сервера.

Ошибки исполнения приходят с HTTP 200 и полем `errors`. Ошибки **валидации** — с
HTTP 400: до исполнения дело не дошло.

## База данных

Схема в `prisma/schema.prisma`, таблицы и колонки в snake_case через `@map`.

### Инварианты закреплены в СУБД

Два правила выражены ограничениями, а не только логикой приложения:

```sql
CHECK ("id" = 1)                                    -- профиль ровно один
CHECK ("url" IS NOT NULL OR "repo_url" IS NOT NULL) -- у проекта есть ссылка
```

Prisma такого не выражает — строки дописаны в миграции вручную.

### Навыки профиля и стек проекта

Поле `Skill.isCore` разделяет два разных утверждения: «освоил» и «использовал в
проекте». В список навыков профиля попадают только освоенные; стек проекта
показывает всё, что в нём действительно применяется. Наружу флаг не выставлен —
это внутреннее различие, а не часть контракта.

### Миграции

Версионированный SQL в `prisma/migrations/`, применяется командой `migrate deploy`
— она накатывает недостающее и ничего не пересоздаёт. Схема базы не
синхронизируется «магией» при старте.

## Сид

`src/seed/` — оркестратор и по файлу на сущность. Три свойства:

**Идемпотентность.** Всё через `upsert` по стабильным ключам. Повторный запуск не
создаёт дублей — сид выполняется при каждом старте контейнера.

**Синхронизация.** После обновления каждый сидер удаляет строки, которых нет в
файлах данных. Файлы в `src/seed/data/` — источник истины, а не начальное
наполнение: убрал навык из файла, он исчезнет из базы вместе со связями.

**Атомарность.** Всё наполнение в одной транзакции. Упавший на середине сид не
оставит базу с половиной обновлённого контента.

Личные данные (ФИО, контакты) приходят из окружения. В репозитории — заглушки,
реальные значения подставляются при деплое.

## Конфигурация

Переменные окружения проверяются zod-схемой при старте. Кривой конфиг роняет
приложение сразу, а не на первом обращении к базе. Валидатор возвращает
разобранный объект, поэтому `APP_PORT` приходит числом и приведение типов не
размазано по коду.

Креденшелы заданы в одном месте, `POSTGRES_DSN` собирается из них подстановкой
внутри `.env`. Менять пароль надо в одной строке.

## Что происходит при `docker compose up`

1. Поднимается postgres, compose ждёт его healthcheck.
2. Стартует контейнер приложения, entrypoint накатывает миграции.
3. Выполняется сид.
4. Запускается Node, приложение слушает порт.
5. Docker опрашивает `/health` — проба ходит в базу, а не просто отвечает «жив».

Приложение не стартует, пока база не готова, и не считается здоровым, пока не
может ответить на запрос.

### Детали образа

Двухстадийная сборка. Клиент Prisma генерируется на стадии сборки: в седьмой
версии это TypeScript-исходники, они компилируются вместе с остальным кодом.

`CMD` в exec-форме — иначе PID 1 занял бы шелл, SIGTERM не дошёл бы до Node и
graceful shutdown существовал бы только на бумаге. Флаг `--enable-source-maps`
делает стек-трейсы указывающими на исходники, а не на скомпилированный JS.

Проба здоровья написана на `node -e` с глобальным `fetch`: в slim-образе нет ни
`curl`, ни `wget`.

`NODE_ENV` задаёт образ, а не compose. Иначе локальный `.env` с `development`
протекал бы в контейнер, и приложение пыталось бы писать `schema.gql` в каталог,
принадлежащий root.

## Тесты

**Unit** — сервисы и чистые функции с моками, без базы: маппинг, фильтрация
аргументов, правило глубины, раскладка результатов DataLoader.

**E2E** — против живой базы: запрос из текста задания дословно, ленивость,
батчинг, отказ на глубоком запросе, редирект с корня.

Типы проверяет `tsc`, а не ts-jest: последний резолвит `@apollo/server` иначе и
спотыкается о две копии одного типа (корневые типы пакета из ESM, типы подпути
через `exports` — из CJS).

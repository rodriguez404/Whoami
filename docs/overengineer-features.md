# Что намеренно не сделано

Список того, что нужно продуктовому сервису, но чего в этом проекте нет —
с причиной и с условием, при котором решение изменилось бы.

Здесь нет пунктов «не успел». Каждый рассматривался и был отклонён.

## Наблюдаемость

### Структурные логи

Продуктовому сервису нужен JSON-лог с идентификатором запроса, чтобы собирать
цепочку по одному обращению. Ставится за десять строк (`nestjs-pino`).

**Почему нет.** Read-only API на один экран данных, без фоновых задач и без
сценариев, где нужно восстановить последовательность действий. Встроенного
логгера Nest достаточно, а лишняя зависимость окупается только при наличии
агрегатора.

**Когда понадобится.** Как только появится хоть одна операция записи или
внешний вызов, который может частично упасть.

### Метрики и трейсинг

Prometheus, OpenTelemetry, гистограммы времени ответа.

**Почему нет.** Метрики нужны, когда есть за чем следить: нагрузка, деградация,
SLA. У визитки нет ни того, ни другого, а инструментирование ради круглого
дашборда — самообман.

## Данные и производительность

### Кэширование

Ответ на `profile` меняется только при деплое, так что кэш дал бы почти
стопроцентное попадание.

**Почему нет.** Экономить нечего: полный запрос со всей вложенностью стоит
11 SQL-запросов к локальной базе. Кэш добавил бы инвалидацию и класс ошибок
«отдаём устаревшее» ради выигрыша, которого никто не заметит.

**Когда понадобится.** При заметном трафике — тогда естественный вариант это
HTTP-кэш на nginx, а не слой внутри приложения.

### Пагинация

Cursor-based пагинация по спецификации Relay для списков.

**Почему нет.** Все коллекции целиком помещаются на один экран: два десятка
навыков, четыре места работы, два проекта. Пагинация на таких объёмах — это
интерфейс ради интерфейса.

### Ограничение сложности запроса

Помимо глубины, запрос можно утяжелить шириной: запросить сотню полей на одном
уровне. Считается через `graphql-query-complexity`.

**Почему нет.** Схема маленькая и не содержит дорогих полей — потолок стоимости
задаётся самой схемой. Ограничения глубины хватает, потому что единственный
способ раздуть запрос здесь это цикл навык -> проекты -> навыки.

### Персистентные запросы

Клиент шлёт хеш вместо текста запроса.

**Почему нет.** Осмысленно при собственном фронтенде и заметном трафике.
Здесь клиент — песочница, которой нужны произвольные запросы.

## Безопасность

### Мутации и авторизация

**Почему нет.** API read-only по замыслу. Содержимое приходит из сида,
редактировать его через сеть незачем. CRUD и токены здесь были бы кодом,
который никто не вызывает.

### Миграции под отдельной ролью — владельцем схемы

Правильная схема для мультитенантных систем: приложение ходит под ролью без
права менять структуру, DDL выполняет отдельная роль.

**Почему нет.** Разделение ролей защищает от компрометации приложения, имеющего
права на изменение схемы. У read-only API без пользовательского ввода вектор
атаки отсутствует.

## Архитектура

### Абстракция над репозиторием

Интерфейс, за которым прячется Prisma: в Go его объявил бы потребитель.

**Почему нет.** В TypeScript интерфейсы стираются при компиляции, поэтому для
внедрения зависимости нужен `abstract class` как токен — лишний файл и лишний
уровень косвенности. При одной реализации это не окупается: Nest подменяет
провайдер по токену конкретного класса, так что для тестов абстракция не даёт
ничего.

**Когда понадобится.** При втором источнике данных или при реализации, которую
надо подменять в рантайме.

### Локализация контента

Хранить тексты на двух языках и отдавать по аргументу `locale`.

**Почему нет.** Удваивает контент и усложняет схему ради витрины. Английская
версия имеет смысл как отдельное решение, а не как параметр запроса.

### Вынос миграций в отдельный сервис

Сейчас миграции и сид выполняет entrypoint контейнера приложения, поэтому в
рантайм-образе лежит CLI Prisma со всем инструментарием генерации.

**Почему нет.** Замеры: образ 916 МБ, из них база 248 МБ. Без Prisma Studio —
855 МБ, без всего инструментария — 625 МБ. Но чтобы убрать инструментарий,
миграции пришлось бы запускать отдельным сервисом, а ему нужен собственный образ
с полным деревом зависимостей: суммарно на диске стало бы **больше**.

При этом контейнер приложения потребляет 35 МБ памяти, а тяжёлый слой
пересобирается только при смене `package-lock.json` — обычный релиз везёт по сети
изменившийся `dist`, то есть килобайты. Это вопрос дисковой гигиены, а не
работоспособности.

Ручная чистка `rm -rf` проверена и отклонена: удаление пакета оставляет поднятые
на верхний уровень зависимости (после удаления Prisma Studio в образе остаются
React и библиотека раскладки графов), и список пришлось бы поддерживать вечно.

## Что сделано и почему именно это

Четыре вещи, которые выглядят необязательными для визитки, но остались:

**DataLoader.** Не оптимизация, а корректность: без него вложенный запрос
порождает N+1, и это ровно то, ради чего в задании просили «работу GraphQL с
вложенными данными».

**Ограничение глубины.** Единственная защита, которую нельзя вынести на nginx:
циклический граф позволяет составить дорогой запрос, а reverse proxy не понимает
GraphQL и такой запрос не отличит.

**Идемпотентный сид с синхронизацией.** Сид выполняется при каждом старте
контейнера, поэтому обязан быть безопасным при повторе. Удаление строк, которых
нет в файлах данных, делает файлы источником истины, а не начальным наполнением.

**Graceful shutdown.** Стоит одной строки и закрывает соединения с базой штатно.
Отсутствие проявилось бы редко, но заметно — контейнер убивался бы по таймауту.
